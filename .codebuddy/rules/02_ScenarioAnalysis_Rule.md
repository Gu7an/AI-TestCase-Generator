# Scenario Analysis Rule

## Objective

建立测试场景矩阵，确保测试用例不是简单覆盖需求句子，而是覆盖需求背后的业务规则和风险。

---

# Scenario Dimensions

每个功能必须检查：

```text
正常流程
异常流程
反向流程
边界
数据
状态
权限
网络
API
第三方依赖
重复操作
并发
中断恢复
兼容性
性能
上下游
跨模块
历史回归
```

性能与稳定性至少考虑：

- 冷启动与首屏加载耗时
- 大数据量下的列表滚动、渲染与内存
- 大文件/多媒体的上传、保存耗时与内存
- 长时间操作（录音、连续使用）的内存与稳定性
- 后台任务进行中界面是否阻塞
- 弱网下的加载与超时降级
- 高频操作（快速切换、连点）的响应与页面栈管理

# 2. Exception

识别：

### 输入异常

- 空
- null
- 格式错误
- 非法值
- 超长
- 超范围

### 业务异常

- 条件不满足
- 状态不允许
- 对象不存在
- 对象已失效
- 重复操作

### 系统异常

- API失败
- API超时
- 数据库异常
- 缓存异常
- MQ异常
- 第三方异常

# 3. Boundary

对于具有范围约束的字段，至少考虑：

```text
min-1
min
min+1
正常值
max-1
max
max+1
```

对于长度：

```text
0
1
最小允许长度
最大允许长度
最大长度+1
```

对于时间/日期，必须额外检查：

- 跨天：23:59:59 与 00:00:00 的操作归属（数据归属哪一天）
- 跨月：1月31日 / 2月28日 / 2月29日（闰年）的周期计算
- 时间点边界：权益到期当日 vs 次日、有效期最后一秒
- 区间边界：如「近7天」必须验证第 7 天可见、第 8 天不可见
- 数量区间边界：如「前3条」必须验证第 3 条可见、第 4 条不可见
- 时区与夏令时：跨时区操作的数据归属
- 系统时间被篡改：修改设备时间能否绕过限制/提前获得内容

若涉及付费、配额、有效期，时间边界为必测项。

禁止以「需求未定义」为由跳过时间边界分析。

如果需求没有定义边界：

```text
不得自行编造业务边界
```

可以记录：

```text
需求待确认：边界值未定义
```

# 5. Concurrency

仅在存在并发风险时分析：

```text
同一用户多端
多个用户
多个请求
同时修改
同时提交
状态变化过程中再次操作
```

重点：

- 数据一致性
- 状态一致性
- 幂等
- 锁
- 最终状态

---

# 7. Compatibility

分析：

```text
新数据
旧数据
历史数据
升级前数据
升级后数据
旧版本客户端
新版本客户端
```

---

# 8. Combination

禁止生成完整笛卡尔积。

例如：

```text
角色 × 状态 × 数据 × 网络 × 权限
```

只生成高价值组合：

- 高风险
- 核心业务
- 边界
- 异常
- 历史缺陷
- 容易造成数据错误

---

# 9. Historical Regression

历史测试用例分类：

```text
复用
修改
废弃
不适用
历史缺陷回归
```

历史缺陷优先级高于普通重复验证。

# 10. Domain Risk Checklist

场景矩阵完成后，必须按被测对象的平台与业务类型，
使用 07_DomainRiskChecklist_Rule.md 中的领域清单逐项交叉校验。

用法：

1. 从 07 中选择与本次需求相关的领域（如 iOS 内购、推送、AI 服务）
2. 逐项确认是否有对应用例
3. 未覆盖项必须补充，或标注 N/A 并说明原因
4. 结果记入 06_TestCaseOutput_Rule 中的「领域清单覆盖率」

禁止仅依赖需求文档推导场景。

需求文档未提及但属于领域标准风险的项目，同样必须覆盖。
