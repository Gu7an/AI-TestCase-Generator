# Test Case Generation Rule

## Preconditions

生成测试用例前必须已经完成：

- 01_RequirementAnalysis_Rule
- 02_ScenarioAnalysis_Rule

禁止跳过前置分析。

---

# Required Fields

每条测试用例必须包含：

```text
用例ID
一级模块
二级模块
前置步骤
用例名称
测试点
优先级
操作步骤
预期结果
```

字段说明：

```text
用例ID   ：格式见下文 Case ID 一节
前置步骤 ：执行本用例前必须完成的准备（账号、权限、设备状态、已有数据等）
```

---

# Test Objective

一条用例只对应一个明确测试目标。

禁止：

```text
一个用例验证多个无关目标
```

同时禁止：

```text
同一个目标拆成多个无意义用例
```

---

# Test Case Name

推荐格式：

```text
验证 + 测试目标 + 条件/场景
```

例如：

```text
验证正常订单可以成功创建
验证订单金额达到最大值时可以正常创建
验证未登录用户无法创建订单
验证已取消订单无法再次支付
```

---

# Test Point

必须明确回答：

```text
本用例验证什么？
```

禁止：

```text
测试功能是否正常
验证系统功能
验证接口
```

---

# Steps

操作步骤必须：

- 可执行
- 有顺序
- 前置条件明确
- 数据明确
- 操作对象明确

禁止：

```text
正常操作
输入正确数据
检查结果
```

---

# Expected Result

预期结果必须可验证。

根据实际需求检查：

```text
页面表现
接口返回
业务状态
数据库数据
关联数据
```

禁止只写：

```text
操作成功
系统正常
符合预期
```

---

# Traceability

每条测试用例必须记录来源：

```yaml
traceability:
  requirement:
  feature:
  business_rule:
  scenario:
  risk:
  historical_defect:
```

至少存在一个有效来源。

---

# Case ID

格式：

```text
项目简写_模块前缀_三位序号
```

例如：

```text
XH_ORD_001
XH_ORD_002
XH_ORD_003
```

不得重复。

---

# Generation Order

禁止按需求文档的叙述顺序生成用例。

生成顺序必须为：

```text
1. 高风险场景（资损、数据安全、核心链路中断、并发、权限）
2. 核心业务流程
3. 状态转换与异常分支
4. 边界与数据场景
5. 兼容性场景
6. 静态展示类（图标、文案、静态元素、样式）
```

控制原则：

```text
静态展示类用例总数不得超过用例总数的 10%

若某个高风险场景无对应用例，而静态展示类用例有多条，
判定为用例设计不合格，必须返工
```

---

# Quantity

不设置固定测试用例数量。

原则：

```text
覆盖充分 > 用例数量
```

如果只有3个有效场景，就生成3个。

不得为了数量增加无意义用例。
