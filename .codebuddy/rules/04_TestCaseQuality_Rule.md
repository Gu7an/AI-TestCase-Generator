# Test Case Quality Rule

## Objective

第一次生成测试用例后，必须进行第二轮独立质量检查。

禁止生成后直接输出。

---

# 1. Requirement Coverage

建立：

```text
需求
 ↓
业务规则
 ↓
测试场景
 ↓
测试用例
```

检查：

- 核心需求是否覆盖
- 核心业务规则是否覆盖
- 异常是否覆盖（按 2.1 判定标准统计，不含业务规则拦截）
- 边界是否覆盖（含时间/日期边界）
- 数据是否覆盖
- 状态是否覆盖（含业务对象生命周期中每个「进行中」状态被中断的场景）
- 权限是否覆盖
- 依赖是否覆盖（对照 01_RequirementAnalysis_Rule 第 8 节依赖清单逐条核对）
- 领域清单是否覆盖（对照 07_DomainRiskChecklist_Rule 逐条核对）
- 历史缺陷是否覆盖

---

# 2. Coverage Checklist

逐项检查：

```text
[ ] 正常
[ ] 异常
[ ] 反向
[ ] 边界
[ ] 数据
[ ] 状态
[ ] 权限
[ ] 网络
[ ] API
[ ] 第三方
[ ] 重复
[ ] 并发
[ ] 中断恢复
[ ] 兼容
[ ] 上下游
[ ] 跨模块
[ ] 历史回归
```

如果发现遗漏：

```text
自动补充测试场景
→ 自动生成测试用例
→ 再次检查
```

---

# 2.1 Dimension Criteria

统计覆盖率前必须先判定场景归属，禁止凭印象归类。

异常场景（计入「异常」）必须满足以下之一：

- 系统异常：接口失败、超时、脏数据、字段缺失、服务不可用
- 网络异常：断网、弱网、超时、网络切换
- 依赖异常：第三方服务失败、权限被拒绝、票据校验失败
- 中断异常：进程被杀、来电中断、切后台、支付中断

以下不计入异常场景，单独计为「业务规则场景」：

- 必填项未填写的拦截
- 配额/次数超限的拦截
- 未订阅用户的付费内容拦截
- 空内容保存校验
- 状态不允许的操作拦截（正常预期内的禁用）

原因：

```text
业务规则拦截属于正常预期路径
计入异常会掩盖系统/网络/依赖维度的真实缺口
```

每个用例只能归入一个主维度，重复计数的需说明。

---

# 3. Duplicate Check

两个用例满足以下条件时判定为重复：

```text
测试目标相同
+
测试条件相同
+
预期结果相同
```

处理：

```text
合并
```

---

# 4. Invalid Case

删除：

- 无需求依据
- 无业务依据
- 与当前需求无关
- 语义重复
- 无法执行
- 无法验证
- 为数量产生

---

# 5. Step Validation

检查：

```text
前置条件
测试数据
操作对象
操作顺序
操作完整性
```

---

# 6. Expected Validation

预期结果必须：

```text
明确
具体
可验证
与需求一致
与操作对应
```

---

# 7. Quality Questions

逐条测试用例回答：

```text
Q1 为什么要测？
Q2 测试依据是什么？
Q3 测试目标是什么？
Q4 步骤是否可执行？
Q5 结果是否可验证？
Q6 是否与其他用例重复？
Q7 优先级是否合理？
```

任何一项不通过：

```text
修改
或
合并
或
删除
或
需求待确认
```

---

# Final Gate

质量检查完成后，必须确认以下三项均已通过：

```text
[ ] 依赖清单中每个依赖均有对应用例ID
[ ] 业务对象生命周期的每个「进行中/已失效」状态均有对应用例
[ ] 领域风险清单中相关领域的每一项均已覆盖或标注 N/A
```

任一未通过，不得进入：

```text
Priority Analysis
```
