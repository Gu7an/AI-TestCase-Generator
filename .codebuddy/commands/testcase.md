---

## description: 使用 AI 测试分析 Agent 完成测试用例分析，并在用户明确要求时生成自动化测试脚本

# Test Case Command

使用 `test-analyst` Agent 执行测试分析。

使用：

`test-case-generation` Skill。

---

# 1. 默认测试流程

必须按照以下流程执行：

```text
需求理解
→ 需求分析
→ 功能拆解
→ 业务规则分析
→ 场景分析
→ 领域风险分析
→ 风险场景补充
→ 测试用例生成
→ 质量检查
→ 覆盖率检查
→ 遗漏补充
→ 去重
→ 优先级
→ 冒烟测试
→ 最终输出
```

不得跳过：

* 需求分析
* 领域风险分析
* 质量检查
* 覆盖率检查

测试用例必须具备：

* 明确测试目标
* 明确前置条件
* 可执行步骤
* 明确测试数据
* 可验证预期结果
* 可追踪测试依据

---

# 2. 信息不足处理

如果需求信息不足：

1. 明确指出缺失信息
2. 不得虚构需求或业务规则
3. 不得虚构接口、参数、页面元素等信息
4. 不影响核心分析时，可以使用明确标记的假设
5. 影响核心结论时，标记为 `阻塞项`

格式：

```text
需求待确认：<缺失信息>
```

或：

```text
假设：<假设内容>
影响：<影响范围>
```

---

# 3. 自动化触发规则

**默认不生成自动化脚本。**

只有用户明确要求以下内容时，才进入自动化流程：

* 生成自动化脚本
* 编写自动化脚本
* 测试用例转自动化脚本
* 生成 Appium 脚本
* 生成 UI 自动化
* 生成 API 自动化
* 生成 Pytest 自动化
* 生成自动化测试项目
* 将测试用例转换为 Python 自动化代码

如果用户只要求：

* 测试分析
* 测试场景
* 测试用例
* 测试用例优化
* 测试覆盖率分析

则**不得主动生成自动化脚本**。

---

# 4. 自动化脚本流程

用户明确要求自动化时，在完成测试用例分析后继续执行：

```text
测试用例
→ 自动化可行性分析
→ AUTO / PARTIAL / MANUAL 分类
→ 自动化类型识别
→ 自动化数据与依赖分析
→ 自动化项目设计
→ Page Object / API 封装设计
→ 测试脚本生成
→ 自动化质量检查
→ 测试用例与脚本映射
→ 最终输出
```

---

# 5. 自动化可行性

每条需要转换的测试用例必须判断：

### AUTO

可以稳定自动执行和验证。

### PARTIAL

部分步骤可以自动化，剩余步骤需要人工处理。

必须明确：

* 自动化部分
* 人工部分
* 原因

### MANUAL

当前条件下无法可靠自动化。

必须说明原因，不得为了生成代码而强行自动化。

---

# 6. 自动化类型

根据测试对象选择自动化类型：

### UI Automation

技术栈：

```text
Python + Pytest + Appium
```

流程：

```text
测试用例
→ 页面分析
→ 元素定位分析
→ Page Object
→ 等待策略
→ 操作封装
→ 断言
→ Pytest 测试脚本
```

### API Automation

技术栈：

```text
Python + Pytest + requests
```

流程：

```text
测试用例
→ API 信息分析
→ 请求参数分析
→ 数据准备
→ 请求封装
→ 响应断言
→ Pytest 测试脚本
```

UI 和 API 自动化必须保持独立，不得混合生成。

---

# 7. 自动化信息约束

自动化脚本必须基于真实测试依据生成。

禁止虚构：

* URL
* HTTP Method
* Header
* Token / Auth
* Request Body
* Response
* 页面元素
* resource-id
* XPath
* 账号
* 测试数据
* 运行环境

缺少必要信息时：

```text
MANUAL / BLOCKED
```

并明确缺失信息。

---

# 8. 自动化项目输出

如果用户要求生成完整自动化项目，应输出：

```text
项目目录
+
测试脚本
+
公共封装
+
配置
+
测试数据
+
pytest 配置
+
requirements.txt
+
README
+
执行方式
```

UI 和 API 项目根据实际需求分别组织，不创建无意义的目录和文件。

---

# 9. 测试用例与脚本追踪

自动化完成后必须建立：

```text
测试用例 ID → 自动化脚本
```

例如：

```text
TC_LOGIN_001 → test_login_success
TC_LOGIN_002 → test_login_invalid_password
TC_LOGIN_003 → MANUAL
```

测试用例 ID 与 Python / Pytest 函数名分离。

---

# 10. 自动化质量检查

生成脚本后必须检查：

* 项目结构
* UI / API 职责分离
* 定位策略
* 等待策略
* 断言
* 测试数据
* Fixture
* 异常处理
* 重复代码
* 硬编码
* Pytest 测试发现
* 测试用例 ID 追踪
* 执行依赖
* 环境要求

不得使用猜测信息补齐代码。

---

# 11. 最终输出

## 普通测试任务

输出：

```text
测试分析
+
测试场景
+
测试用例
+
覆盖率 / 风险 / 遗漏分析
+
优先级
+
冒烟用例
```

## 自动化任务

在上述内容基础上增加：

```text
自动化可行性分析
+
AUTO / PARTIAL / MANUAL
+
UI / API 分类
+
项目结构
+
自动化脚本
+
测试用例 → 脚本映射
+
执行说明
+
无法自动化项及原因
```

---

# 12. 核心约束

必须始终遵守：

```text
测试用例 ≠ 自动化脚本
```

生成测试用例不会自动生成脚本。

只有用户明确要求自动化时：

```text
测试用例
→ 自动化分析
→ 脚本生成
```

自动化过程中：

```text
UI ≠ API
AUTO ≠ 必须自动化
风险 ≠ 业务规则
假设 ≠ 事实
代码完整 ≠ 信息真实
```

任何关键测试依据或自动化信息缺失时，必须明确说明，不得自行编造。
